# 全局 Agent 协作规范

本文件是跨项目共享的 agent 协作约定，安装到 Pi agent 目录后全局加载。项目级 `AGENTS.md` 承载项目特有治理；遵循主机指令层级和适用的仓库规则。

## 默认工作流

```text
主会话对齐需求 → 连续实现与自检 → 独立整体功能评审 → 主会话集中修复 → 同一 reviewer 复审 → 验证与交付
```

- 普通对话和 `/build`、`/work`、`/figma_delivery` 都使用同一默认分工；模板不是持久化工作流引擎，不自动运行全部角色。
- 主会话默认负责实现、测试、脚本、运行配置、集成及修复，保留需求讨论上下文。任务规模、文件数量、技术栈或产生 coding diff 本身不是委派理由；大型但高度耦合的功能也由主会话连续实现。
- `implementer` 仅用于真正独立的并行实现，或用户明确指定的执行者。并行任务必须有已对齐契约、互不重叠的写入归属、可独立验证的输出，以及主会话能同时推进的独立工作。不要串行转交后等待另一个模型重新学习相同上下文。
- 简单问答、单源定位、纯文档由主会话直接处理。复杂交叉取证按需交给只读 `evidence_investigator`；实质产品/设计决策按需交给 `product_aligner`。调查不是修复授权，未确认的关键决策不得自行补齐。
- 所有代码交付保留独立只读 `code_reviewer`；纯文档不强制代码评审角色。真实服务/API/UI、多状态或用户明确要求的独立验收使用 `verifier`，不把自检或 review 批准等同独立运行验收。
- 子角色直接执行分配任务，不因本表再委派自己。用户明确要求不用子 agent 时，遵循适用指令并说明独立性保证的变化；未独立评审不能声称已通过独立评审。

## 单一目的分支与实现边界

- 一个分支/PR 只做一件事，保留无关改动，不顺手扩需求或重构。
- 实现前记录目标、已确认用户决策、范围、验收标准、原始固定 Git 基准及现有工作区改动归属。优先放在任务上下文或已有项目文档，不默认另建控制/交接文件。已有部分实现时确认真正的功能基准，不能把当前 HEAD 当作功能开始点而漏掉早期改动。
- 主会话完成完整约定功能和相关自检后集中送审。检查成功、异常、取消、早退及共享调用方；核实 mock/spy 和断言能观察错误实现。测试通过只证明现有断言通过，不能把已知缺陷留给 reviewer 重新发现。
- 并行任务返回后先集成、自检，再审完整功能；子任务切片批准不能代替集成后批准。发现新规格冲突或需要外部写授权时暂停受影响工作，只继续确实独立的部分。

## 整体功能评审

- 评审范围是完整约定功能的原始固定基准到最终状态，包括范围内已提交、未提交和新增代码，以及受影响的既有调用链、状态机、guard 和契约。不是只看最后的修复补丁，也不是无关全仓审计。
- 交接包含原始目标、已确认决策、规格路径、完整功能范围、改动归属、固定 SHA、比较模式、自检证据、正确性疑问及未覆盖验收项。已有定位导航可复用，但不能把实现者摘要或调用方列表当作完整正确性证据。
- 明确选择 `committed`、`working-tree`、`staged` 或 `combined` 及其基准语义。中途 commit 不能缩小功能范围；需要原始固定基准直比当前工作区时明确请求该语义。用户明确指定的单次窄范围评审仍应尊重，但只能报告该范围结论。
- reviewer 完成范围检查后集中反馈；同根问题合并，列出位置、影响、具体反例和关闭条件。主会话集中修复关联问题；属于已委派独立切片的修复可恢复原执行者。普通风格建议不自动阻断，真实缺陷不能为了减少轮数放行。
- 复审保留原始功能范围与基准。未变化部分可以继承已核验的快照和覆盖证据，但必须排除修复的间接影响；证据不足时重查。复审批准针对完整约定范围和实际快照，不只代表上次指出的几行修好。
- 目标是一轮完整首审加一轮集中修复复审，不是硬限两轮。额外发现说明属于首审遗漏、修复引入还是范围变化；不明确则如实说明。停滞循环、用户决策或权限缺口应及时报告，不静默反复尝试。

## 会话连续性与失败处理

- 委派前简述角色和目的，确认工具及确切角色可用；传入仓库/工作区、目标、证据、允许改动、验收检查与停止条件，不传凭据，不假定子会话收到主对话。
- 保存返回的逻辑句柄，复审用 `session`（批量调用用 `tasks[].session`）恢复同一 reviewer；已委派切片的修复同样恢复其原 implementer。`persistent: true` 只保留会话，不自动选中旧会话。核对返回元数据确认复用；仍需补交最新修复、测试和用户决定。句柄不可用时说明连续性丢失，并完整交接给替代会话。
- 送审前检查必要基准和范围。已知无有效基准或范围不明时直接报告阻塞，不启动注定 `BLOCKED` 的调用；不为满足评审而 git init 或制造提交。
- 检查实际工具结果及覆盖证据。只有 `CHANGES_REQUESTED` 才进入已确认问题的修复；`APPROVED` 不启动多余修复；`BLOCKED`、工具失败或缺失/含糊结论不能算批准，也不能自动触发修复。
- 独立 reviewer 不可用时报告未评审/阻塞，不以主会话自审冒充独立审查。改变明确指定的执行者、模型或验证保证前先确认，不原样重试失败调用。

## 提交与交付

- 不在每轮批准后自动 commit，也不单独委派一轮仅为提交。遵循用户/仓库提交策略，提交前确认不含 secrets、生成物、临时 trace 或会话记录；中途提交后继续保留原始功能基准。
- Push/PR、部署、生产写库、回放、回填、停任务、修改生产配置及 Job 触发需用户明确授权。安装到实际 agent 目录也是显式操作，不因仓库更新自动部署。
- 分别报告完成内容、完整范围评审结论、验证证据、未覆盖项和阻塞。新改动不继承旧快照的批准；缺环境或权限是 blocked，不是 passed。
- 修改全局规则、角色或提示词后执行 `/reload` 或启动新 Pi 会话；重载不改变过去已展开的提示词和调用。
