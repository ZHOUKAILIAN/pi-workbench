# Figma

目标：
$ARGUMENTS

## 链路

```text
对齐 -> 执行 -> 评审 -> 验证
```

## 分工

- 对齐：主会话确认设计、页面状态、需求与 API 边界；有实质决策时按需使用 `product_aligner`。
- 执行：主会话连续按确认设计和 CSS 规范实现、自检、修复。`implementer` 仅用于契约明确、写入不重叠、可独立验证且主会话同时有独立工作的并行子任务，或用户明确指定。
- 评审：独立 `code_reviewer` 整体检查完整约定 UI 功能、关联状态/调用链及 Standards 与 Spec/设计符合度。
- 验证：`verifier` 对照设计与实际渲染独立验证；代码批准不替代视觉/交互验收。

不要因为阶段存在就强制转交实现。并行实现先集成和自检再整体评审。只读设计审计或单纯咨询不使用此交付入口。

## 要求

1. 自己提取 Figma/页面/状态/代码位置；缺设计权限或实际页面时明确 blocked。
2. 先对齐设计与需求/API，再实现。用户要求先确认时，输出边界后停住。
3. 优先使用已安装的 figma-design-audit、css-best-practices、figma-restoration-review 等对应技能；缺少必需能力时报告安装缺口，不假装已读设计或完成还原。
4. 实现前记录原始固定功能基准、已确认设计/需求决定、范围及已有改动归属。完整实现与相关成功/异常/取消/早退、共享调用方自检完成后审原始基准至最终状态的完整功能及关联调用链；明确模式和比较语义，中途 commit 不得隐去早期实现，不只审最后补丁。已知缺基准/范围时先报告阻塞，不为评审制造提交。
   核心缺陷尚未修复或存在真实阻塞时不送正式评审，不让 reviewer 重复发现或确认。reviewer 首审允许充分查证，完整检查约定范围和同类状态后集中返回问题、反例和关闭条件，不发现一条就交回。
   仅 CHANGES_REQUESTED 启动主会话成批修复关联问题、同类遗漏及自检问题，完成后再请求复审；普通风格建议不自动触发循环。BLOCKED 写清未完成事项、依据、原因、影响与解除条件后暂停受影响工作，不再额外评审同一阻塞；有解除条件、新证据或明确决定后才恢复。普通可修复缺陷不当阻塞，工具失败先查明原因，APPROVED 不启动多余修复。
   复审传回原 reviewer 的 session 句柄并核对元数据，persistent: true 不是恢复；补交最新状态、测试和已确认决定，保留原基准与完整功能范围。未变化部分可继承已核验且不受间接影响的证据；句柄不可用时说明并完整交接。目标完整首审加集中修复复审，不硬限轮数，不以速度、问题数量或报告长度衡量质量；额外问题说明遗漏/修复引入/范围变化，同根问题连续遗漏时检查覆盖与交接质量。未经复审批准不声称完成。
   评审后再验证实际渲染与设计边界；critical/major 必须处理并复评，不把窄范围批准当整体功能或实际渲染已通过。
5. 模型配置由 Pi agent 目录的 `agents/*.md` 承载，默认不绑定具体型号。私有 local 配置的 `agentModels` 是安装输入；未绑定时子进程使用 Pi 默认模型设置。
6. 模型调用失败时报告失败阶段与原因；没有显式配置并授权的 fallback 就停止，不写死某个兜底模型、不承诺链路永不中断。需要改变用户明确指定的执行者、模型或独立验证保证时先征得同意；主会话默认实现不需要另行确认。
7. 缺权限或业务冲突时停下说明。Push/PR、部署仅在用户明确要求后执行。

## 输出

边界理解、改动、评审结论、验证证据、偏差、待决策。
