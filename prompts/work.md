# 排查

目标：
$ARGUMENTS

## 先选模式

先判断任务属于哪一种，只选一种：

| 模式 | 适用 | 默认动作 |
| --- | --- | --- |
| `explain` | 只问原理、代码含义、错误解释 | 主会话直接回答，不拆 agent |
| `inspect` | 只确认代码、分支、部署或现象 | 主会话取证，输出证据和结论 |
| `investigate` | 需要代码、日志、数据交叉定位根因 | 取证后再决定是否修复 |
| `fix` | 根因或改动边界已经明确 | 主会话最小修改、自检，随后独立评审与适用验证 |
| `delivery` | 明确要求从排查到修复交付 | 取证 -> 修复 -> 评审 -> 验证 |

简单任务不要为了遵守流程而拆 subagent。主会话默认连续负责实现、自检和修复；子角色只用于独立判断、明确价值的取证/对齐/验收或真正独立的并行实现，不串行转交相同上下文。独立代码评审仍是代码交付门槛。

## 任务契约

开始时用不超过 8 行明确：

- 目标：要回答什么或交付什么
- 范围：仓库、分支、环境、时间窗、涉及模块
- 完成标准：什么证据算完成
- 当前模式：`explain` / `inspect` / `investigate` / `fix` / `delivery`
- 风险：是否涉及生产写、数据库写、回放、回填、Job、配置或 Push/PR

能从代码、文档、日志、数据中确认的事实自行查；只有会改变范围、环境、写入或验收标准的决策才问用户。一次只问一个最短阻塞问题。

## 调查链路

```text
现象 -> 可验证问题 -> 证据 -> 根因状态 -> 修复 -> 独立验证
```

要求：

1. 证据必须可复核，至少标出代码路径、日志/时间线、数据状态或反例中的相关项。
2. 根因状态只能是：已证实、未证实、阻塞。证据不足时停在对应状态，不把推测写成结论。
3. 取证阶段默认只读；发现需要写入时先说明写入对象、风险、回滚和所需授权。
4. 根因未证实不得进入修复；自检不替代独立代码评审，也不能冒充独立运行验收。局部确定性检查可由主会话执行，需要独立服务/API/UI或多状态验收时才调用 verifier。
5. Push/PR、部署、生产写库、回放、回填、停任务、改生产配置和 Job 触发仅在用户明确要求后执行。

## Agent 选择

用户角色位于 Pi agent 目录的 `agents/*.md`（默认 `~/.pi/agent/agents`，可由 `PI_CODING_AGENT_DIR` 改写）；可信项目角色位于 `.pi/agents`。角色未指定 `model` 时，子进程使用 Pi 的默认模型设置，不保证跟随主会话临时切换。模型绑定在私有 local 配置的 `agentModels` 中维护并安装，不在 prompt 重复声明。

- `evidence_investigator`：仅在 `investigate` 或复杂 `inspect` 中使用，输出证据账本，不改代码。
- 主会话：根因已证实或方案已确认后直接实现和自检，集中修复评审问题，保持上下文连续。
- `implementer`：仅用于已对齐契约、写入互不重叠、输出可独立验证且主会话同时有独立工作的并行子任务，或用户明确指定；不因代码修改、任务规模或切换模型就调用。
- `code_reviewer`：所有主会话/委派代码交付的独立完整功能评审；纯文档、纯调查和只读任务除外。并行实现先集成，不把切片批准当整体批准。
- `verifier`：独立验收或真实服务/API/UI、多状态行为验证时使用，缺环境/权限明确 blocked；简单 focused check 由主会话执行。
- `product_aligner`：只有产品规则、范围或验收标准存在真实冲突时使用。

模型失败时先报告失败类型和已消耗的阶段；只有控制器或用户明确允许时才换模型重试。不要在 prompt 中承诺未实现的自动 fallback。

## 整体评审与修复

实现前记录原始固定功能基准、已有改动归属、原始目标、已确认决策和验收标准。已有部分实现时确认真正功能起点，中途 commit 不重置基准，不自动提交来制造评审输入。交接原始基准到最终状态的完整功能范围及受影响调用链、自检结果、正确性疑问和未验证项；明确 review 模式/比较语义，纳入适用的已提交、工作区及新增文件，不只审最后补丁，不扩成无关全仓审计。

- 送审前检查基准、范围和已知未解决问题。核心缺陷尚未修复或存在真实阻塞时，不派 reviewer 重复发现或确认；必要技术咨询明确窄范围，不当完整交付批准。
- reviewer 充分查证并完成约定范围后集中返回 findings 与关闭条件；同根问题主动检查同类路径，不发现一条就交回，不以速度、问题数量或报告长度衡量质量。
- `CHANGES_REQUESTED`：主会话成批修复关联问题、同类遗漏及自检问题，再交回复审；普通风格建议不自动开启循环。`APPROVED`：进入适用验证，不调用多余修复。
- `BLOCKED`：写清未完成事项、依据、原因、影响和解除条件，暂停受影响工作，不再额外评审同一阻塞。有解除条件、新证据或明确决定才恢复必要工作；普通可修复缺陷不当阻塞。工具失败或缺失结论先查明原因，执行正常返回不等于业务完成。
- 复审显式传回原 reviewer 的 `session` 句柄并核对返回元数据，`persistent: true` 不等于恢复；补交最新修复、证据和用户决定，保留原基准及完整功能范围。未变化部分可继承已核验且不受间接影响的证据；句柄不可用时说明并完整交接。
- 目标是完整首审加集中修复复审，不硬限轮数，也不承诺首审找全。额外问题解释首审遗漏、修复引入或范围变化；同范围同根问题连续遗漏时检查覆盖和交接质量。没有复审批准的修复不算完成，代码批准也不替代运行验收。

## 阶段输出契约

阶段完成或真实阻塞时集中交接以下信息，不为每个内部进度单独交回：

- `status`: `completed` / `blocked` / `failed`
- `facts`: 已确认事实
- `evidence`: 可复核位置或命令结果
- `decision`: 本阶段结论；blocked 时包含原因与影响
- `next`: 下一阶段及其输入；blocked 时写解除条件，不自动进入下一阶段

最终输出：目标理解、证据链、根因状态、改动说明、验证证据、风险/缺权限/待决策。
