# 排查

目标：
$ARGUMENTS

## 先选模式

先判断任务属于哪一种，只选一种：

| 模式 | 适用 | 默认动作 |
| --- | --- | --- |
| `explain` | 只问原理、代码含义、错误解释 | 主会话直接回答，不拆 agent |
| `inspect` | 只确认代码、分支、部署或现象 | 主会话取证，输出证据和结论 |
| `investigate` | 需要代码、日志、数据交叉定位根因 | 取证后再决定是否修复 |
| `fix` | 根因或改动边界已经明确 | 最小修改，随后独立验证 |
| `delivery` | 明确要求从排查到修复交付 | 取证 -> 修复 -> 评审 -> 验证 |

简单任务不要为了遵守流程而拆 subagent。只有需要上下文隔离、独立判断或明确阶段产物时才拆。

## 任务契约

开始时用不超过 8 行明确：

- 目标：要回答什么或交付什么
- 范围：仓库、分支、环境、时间窗、涉及模块
- 完成标准：什么证据算完成
- 当前模式：`explain` / `inspect` / `investigate` / `fix` / `delivery`
- 风险：是否涉及生产写、数据库写、回放、回填、Job、配置或 Push/PR

能从代码、文档、日志、数据中确认的事实自行查；只有会改变范围、环境、写入或验收标准的决策才问用户。一次只问一个最短阻塞问题。

## 调查链路

```text
现象 -> 可验证问题 -> 证据 -> 根因状态 -> 修复 -> 独立验证
```

要求：

1. 证据必须可复核，至少标出代码路径、日志/时间线、数据状态或反例中的相关项。
2. 根因状态只能是：已证实、未证实、阻塞。证据不足时停在对应状态，不把推测写成结论。
3. 取证阶段默认只读；发现需要写入时先说明写入对象、风险、回滚和所需授权。
4. 根因未证实不得进入修复；修复后不得用执行 agent 的自检代替独立验证。
5. Push/PR、部署、生产写库、回放、回填、停任务、改生产配置和 Job 触发仅在用户明确要求后执行。

## Agent 选择

用户角色位于 Pi agent 目录的 `agents/*.md`（默认 `~/.pi/agent/agents`，可由 `PI_CODING_AGENT_DIR` 改写）；可信项目角色位于 `.pi/agents`。角色未指定 `model` 时，子进程使用 Pi 的默认模型设置，不保证跟随主会话临时切换。模型绑定在私有 local 配置的 `agentModels` 中维护并安装，不在 prompt 重复声明。

- `evidence_investigator`：仅在 `investigate` 或复杂 `inspect` 中使用，输出证据账本，不改代码。
- `implementer`：所有需要产生 coding diff 的任务都必须使用；仅在根因已证实或方案已确认后执行代码改动。
- `code_reviewer`：所有由 `implementer` 产生的 coding diff 都必须使用，不按改动规模或影响面缩减；纯文档、纯调查和只读评审除外。
- `verifier`：所有 `fix` / `delivery` 的终点；优先执行确定性测试、真实接口或状态查询。
- `product_aligner`：只有产品规则、范围或验收标准存在真实冲突时使用。

模型失败时先报告失败类型和已消耗的阶段；只有控制器或用户明确允许时才换模型重试。不要在 prompt 中承诺未实现的自动 fallback。

## 阶段输出契约

每个阶段只输出以下内容：

- `status`: `completed` / `blocked` / `failed`
- `facts`: 已确认事实
- `evidence`: 可复核位置或命令结果
- `decision`: 本阶段结论
- `next`: 下一阶段及其输入

最终输出：目标理解、证据链、根因状态、改动说明、验证证据、风险/缺权限/待决策。
